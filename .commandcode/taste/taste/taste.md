# Taste
- Charts large, multi-session efforts with the `wayfinder` skill — a shared map of decision tickets resolved one at a time — before starting implementation. Works the map one ticket at a time via `$wayfinder tackle ticket <github-issue-url>`, one ticket per session. Confidence: 0.65
- On a wayfinder ticket, treats the GitHub issue as the source of truth over stale local planning docs (closed issues stay closed, not reopened), claims the ticket by self-assigning (`gh issue edit <n> --repo <owner>/<repo> --add-assignee @me`) as the very first write, refers to tickets by title + link, and resolves as: post a resolution comment, close the issue, then append a one-line gist to the map's decisions list rather than restating the full evidence — and only once the whole verification matrix is green. Confidence: 0.65
- Optimizes for shipping fast to real users to get market validation: asks to defer or revise "nitty-gritty" tickets that block shipping, and prefers to keep deferred work open (detached/labeled for later) rather than deleting it. Confidence: 0.7
- Drives feature work through the `ai-devkit` phase skills (`dev-planning`, `dev-design`) to lint and review lifecycle docs. Confidence: 0.6
- Uses one git worktree per feature (e.g. `.worktrees/feature-base-zk-credits`) rather than working on a branch in place, and insists product work stays inside that worktree — a dirty, unrelated checkout in the main tree must never be staged or committed. Confidence: 0.7
- On a ticket inside an already-dirty worktree, snapshots every target file to `/tmp` before the first edit and records a scoped per-file diff review against those snapshots in the resolution evidence, so the session's changes are provably scoped and the pre-existing work is provably untouched. Confidence: 0.6
- For onchain/Base work, requires agents to consult the external `ethskills` SKILL.md guidance (and the `build-on-base` skill) before writing Solidity or shipping anything onchain. Confidence: 0.6
- Keeps security-sensitive findings and internal planning/launch strategy local; rejected a sanitized public issue map as not useful for the team and asked to revert it and keep planning local. Confidence: 0.7
- Biases strongly toward shipping fast ("just want to ship this product fast") while still asking for correctness/design review before proceeding. Confidence: 0.6
- Comfortable delegating decisions to the agent: asks it to present recommendations, then accepts them wholesale ("accept all recommendations") to keep momentum. Confidence: 0.5
- Insists on TDD: write the failing test first and confirm it fails for the right reason before any production code (explicitly, no production Solidity until a failing test), working in vertical slices (failing test → minimum production change → green) with tests written only at pre-agreed public seams. Confidence: 0.8
- Never stages everything — forbids `git add .` in favor of explicit pathspecs, one conventional commit per logical unit via the `dev-commit` skill; commits are not amended, rebased, or force-pushed. Confidence: 0.8
- Treats verification as fresh-only: prior-session logs/tests are not evidence; the listed commands must be run in-session with visible output before work is marked done. For web/app work the gate is lint, typecheck, the unit suite, the production build, the e2e specs, `git diff --check`, and a scoped stale-string / unsupported-claim grep over the changed copy set. Confidence: 0.75
- Treats user-facing copy (READMEs, install guides, landing/metadata, in-app surfaces) as a contract to be enforced by tests: adds a focused test that scans the explicitly enumerated active copy files, requires the truthful claims, and rejects stale commerce/overclaim terms — plus an e2e assertion on the rendered page. Confidence: 0.65
- When editing existing UI, keeps the existing visual system, semantic elements, focus behavior, responsive layout, and concise brand voice intact — no visual redesign, only copy/scoping changes. Confidence: 0.6
- Requires a two-axis code review (standards + spec) of the scoped diff against the baseline HEAD before committing. Confidence: 0.65
- Keeps generated artifacts out of commits (gitignored wasm/r1cs/zkey/ptau/build outputs) and never commits keys or `.env` secrets; deploy credentials live in a Foundry keystore with any password file kept outside the repo. Confidence: 0.6
- Requires a privacy scan over production surfaces: logs, spend-plane rows, dashboard views, and weekly exports must never carry plaintext prompts, responses, secrets, proofs, wallet/account ids, remaining credit, nullifiers, or request signals. Confidence: 0.6
- Requires the same privacy boundary to be stated honestly in user-facing copy: telemetry does not collect prompts/responses/secrets/proofs/nullifiers/request signals/payer joins, while the gateway and the upstream provider can still observe request content and traffic metadata. Confidence: 0.6
- Enforces strict phase scoping: work stops at the committed unit and does not expand into later phases, tickets, or deploys in the same session. Confidence: 0.7
- Names the excluded surfaces explicitly (archives, historical design docs, dormant/backend payment code) and leaves dormant code, routes, and env config intact for a later ticket rather than deleting them in the current one. Confidence: 0.6
- Wants lifecycle docs (planning/implementation/testing/map) kept truthful and in sync with the tree, including negative fixtures and known leaks; forbids overclaiming unverified work (independent review, real Sepolia verifier, onchain activity). Confidence: 0.7
- Records durable per-ticket evidence as a dated "Local <ticket> evidence" section in `docs/ai/testing/<date>-<feature>.md`, with a command → result table and per-file added/removed line counts for the scoped diff. Confidence: 0.6

- Expects an end-of-session report naming the commit SHA(s), the staged-vs-leftover uncommitted files, the exact verification commands run, and — called out rather than buried — the judgment calls that diverge from the plan plus the steps deliberately left undone because the session lacks the authority to do them. Confidence: 0.6

Confidence: 0.6
- Commit messages use a conventional-commit subject scoped by area (`feat(zk-credits):`, `chore(deploy):`, `docs(zk-credits):`) with a substantive multi-paragraph body explaining the reasoning, ending with a `Validation:` line naming the exact commands and pass counts. Confidence: 0.55
- Makes Postgres-backed integration suites deterministic: shared `pg_advisory_lock` plus `runMigrations` in setup so parallel test files cannot race, and runs the full suite twice to prove it is not flaky. Confidence: 0.55
- Prefers fail-closed behavior for security-critical state and configuration: an unreadable launch/kill-switch state refuses work rather than permitting it, cap exhaustion persists a paused state instead of a per-request error, and missing or unreadable verifier/provider config fails readiness. Confidence: 0.6
- Fixes economic and security boundaries (single service class, forced model, request limits, price ceilings, spend caps) in reviewed source rather than exposing them as environment configuration a deploy could widen. Confidence: 0.55
- Enforces a hard plane separation between founder/infrastructure secrets and operator-owned secrets in tooling: launch scripts must reject operator variables while operator scripts reject deployer, sponsor, database, admin-token, provider, and other infrastructure variables; secret env files must be git-ignored and mode 0600; placeholder values are refused; and secrets must never reach logs or evidence artifacts. Confidence: 0.6
- Holds shell/batch automation to the same bar as application code: `bash -n` plus ShellCheck when available, and behavioural tests with fixture env files covering placeholder detection, permission failures, secret-output scans, idempotent reruns, and interrupted-stage recovery. Confidence: 0.55
- Treats published packages as a verified contract: inspects tarball contents, keeps test files out of the published surface, and pins exact immutable versions and hashed artifacts (rejecting unpinned or unknown versions at preflight) rather than ranges or `file:` references. Confidence: 0.55
- For a pilot, prefers free-tier infrastructure (free web tier plus an external free managed Postgres over its direct TLS connection, not the pooled endpoint) and accepts cold-start behavior explicitly rather than paying for always-on instances. Confidence: 0.55
- Wants long, multi-step infrastructure automation to be resumable and safe to retry: deterministic resource names, read-back-and-verify configuration after every write, and a stored state that distinguishes an unknowable outcome ("unknown", from a timed-out non-idempotent call) from a definite failure — an unresolved unknown blocks the next run until it is reconciled against the provider by exact name/configuration, never retried blind. - Requires that automation never take an irreversible or ambiguous action on its own: irreversible steps (publish, broadcast, provision, activate) stop and ask for explicit confirmation, there is deliberately no unattended confirmation flag, no flag ever deletes a provider resource, and a lookup that returns several candidates stops and lists them instead of picking one. Confidence: 0.6
- Stages credential/preflight checks by phase so an early check never demands a credential that cannot yet exist — e.g. deferring a GitHub OAuth client id/secret until the deployed web host has produced the real callback URL. Confidence: 0.5
